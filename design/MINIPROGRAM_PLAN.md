## 2. 两类用户的购买与使用路径

**个人用户：** 浏览服务 → 看清价格和使用规则 → 登录 → 购买 → 在小程序工作台发起 AI 任务 → 查看结果、扣费和余额。

首版建议以已经验证可调用的文本对话/文本处理服务闭环为主。具体可售模型以真实网关测试为准；图片、语音、视频等能力不因 API 文档中有条目就默认开放销售。

**企业用户：** 建立/加入企业空间 → 购买标准化企业额度或套餐 → 分配成员权限和额度 → 在团队工作台使用 AI，或通过 API 接入业务 → 查看企业用量、账单和订单。

标准商品支持自助购买；定制部署、大额采购和电站合作保留咨询路径。两种账户均提供实际使用入口，企业 API 接入可延续网页控制台与开发工具。

个人余额、企业余额、角色和消费记录应分开；同一人可切换个人与企业空间。团队消费按企业权限执行，不能自动动用个人余额。

## 3. 首版信息结构

| 底部入口 | 核心内容 | 用户完成的事 |
|---|---|---|
| 发现 | 服务分类、已开通模型、商品详情、计费说明、购买入口 | 选服务、了解用途和成本 |
| 工作台 | 新建对话/任务、模型选择、历史结果、当前账户和可用额度 | 直接使用已购服务 |
| 订单 | 购买订单、支付状态、消费明细、退款进度；有真实来源时展示产地记录 | 查购买与使用记录 |
| 我的 | 个人/企业空间、余额、成员与额度、API 接入入口、客服和账户设置 | 管理账户及团队 |

工作台中的消费记录与购买订单分别呈现：一次充值/购买不等于一次模型请求。产地卡应关联真实使用记录，不给尚未消耗的充值订单自动生成能源或减排数据。

## 4. 首版必须形成的闭环

1. **账户**：微信身份与平台账户绑定，个人/企业空间及角色边界明确；退出和重新进入后状态一致。
2. **商品**：名称、服务范围、价格、计费单位、有效期和退款规则由服务端提供；未确认的商品不展示可支付按钮。
3. **购买**：服务端创建订单、确认支付结果、幂等发放权益；关闭页面后能查询结果。前端显示支付成功不能单独触发到账。
4. **使用**：小程序经业务服务端调用模型；支持结果返回、中断和错误说明；平台上游密钥不下发到客户端。
5. **计费**：购买余额/权益与消费账本可核对；明确超时、失败、取消、重试的计费规则，避免重复扣费。具体规则由业务确认。
6. **企业**：管理员与成员权限、企业额度、成员限额、消费归属；成员离开后回收访问权限。
7. **售后**：订单查询、退款处理和客服入口；退款与已消耗权益的处理按已确认规则执行。

## 5. 设计与工程复用建议

推荐让网站、小程序共用同一套商品、账户、权限、订单、用量和计费服务。小程序作为独立客户端新增，不复制一套账本。

```text
官网 / 网页控制台 ─┐
                  ├─ 账户与权限 / 商品与订单 / 权益与计费 / 模型调用服务
微信小程序 ────────┘
```

保留现有纸白、晨蓝、暮紫和排线插画；详情与工作台优先保证可读、可点击、可返回。桌面三栏控制台改为底部导航加独立详情页。表格转为摘要卡片，复杂 Key/成员设置进入二级页面。

对话区域采用稳定背景；树影只考虑用于发现页或引导区，并在真机性能验证后启用。中文优先使用可靠的系统字体回退，不能假设网页外链字体在小程序内原样可用。

具体技术栈需结合现有开发团队确定；当前单文件网页不承诺自动转换为小程序。品牌、素材、文案和字段可复用，布局、组件、身份和支付交互需要适配。

## 6. 实施顺序与验收依据

| 阶段 | 交付 | 完成判据 |
|---|---|---|
| 范围与交易定义 | 页面流程、首批可售服务、个人/企业账户规则、计费及退款规则 | 购买对象和消费单位明确，真实服务负责人及接口确定 |
